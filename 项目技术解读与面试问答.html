① 项目全景

1.1 它解决什么问题

医院门诊场景的智能体系统，覆盖患者从问诊咨询 → 挂号 → 检查 → 随访的主链路，并给医护提供审批与病历工作台。

刻意的边界（Tier-0 红线）：不做诊断、不开处方、不给用药剂量。系统只做流程服务与信息组织，临床判断交还医生。这条红线不是"暂时没做"，而是产品定义的一部分——AI 给错了药量会出人命。

③ 技术逐个深度解读

3.A 编排与 Agent

LangGraph编排核心
它解决什么问题
把「多步推理 + 工具调用 + 人工介入 + 长时运行」的状态机管起来。纯 LLM 应用是单轮问答，Agent 应用需要跨轮次保状态、可中断、可恢复、可回放。
为什么是它，而不是别的
方案差别
LangGraph把 Agent 建模成有状态图：节点=步骤、边=流转、checkpointer 负责持久化。interrupt() 是一等公民，天然支持 HITL；配合 Postgres checkpointer，服务重启后审批状态不丢。适合需要人工介入与长事务的业务。
LangChain 原生 AgentExecutor本质是「while 循环 + 工具调用」黑盒，状态不可控、不可中断、不可回放。做 demo 快，但没法在中间插一道人工审批。
CrewAI / AutoGen偏多 Agent 自由对话。灵活但流程不可预测——医疗场景要的是确定性流程（该审批必须审批），不是 Agent 自由发挥。
Dify / Coze低代码平台，快但脱离代码控制。越权校验、PHI 隔离这类横切逻辑很难优雅嵌入；也不利于展示工程能力。
本项目怎么用
src/graph.py 建图；src/supervisor.py 做意图分类（中枢辐射）；src/agents.py 定义 4 个子 Agent。敏感动作用 interrupt() 挂起，审批单落 approvals 表，医护批准后 Command(resume=…) 恢复。checkpointer 用 AsyncPostgresSaver。
⚠️ 踩过的坑
interrupt() 在 resume 时会把节点从头重跑——若重跑时 LLM 不再生成那个敏感调用，会出现「已批准却没执行」。解法：把待审批的 tool_calls 落到 pending_calls 表，resume 时直接读取执行，保证落库确定性。
💬 面试怎么答
别只说"用了 LangGraph"。说清：我需要的不只是多轮调用，是「能中断、能恢复、能回放、跨重启不丢」的状态机——这是选 LangGraph 而非 AgentExecutor 的真实理由。"敏感操作审批如果只存在内存里，服务一重启患者的挂号就凭空消失了，这在医疗场景不可接受。"
中枢辐射 vs 网状编排架构模式
为什么这么选
网状（Agent 互相调用）灵活但调用链不可预测、难追踪、难加全局护栏。中枢辐射（supervisor 统一分发）牺牲了一点灵活性，换来：意图可审计、工具权限可按 Agent 收敛、新 Agent 接入不影响既有链路。
本项目怎么用
4 个子 Agent（triage 分诊 / intake 问诊·报告·病历 / booking 挂号 / followup 随访），各有独立工具命名空间——triage 拿不到 booking 的锁号工具。另有 chat（知识库直出）与 human（审批中断）两条旁路。
contextvars（tenant_ctx / patient_ctx）运行时
它解决什么问题
工具函数需要知道「当前是哪个患者 / 哪个院区」，但工具签名里不能出现这些参数（否则 prompt injection 可操纵）。
为什么是 contextvars，而不是 thread-local 或逐层传参
  • 逐层传参：要把 patient/tenant 一路透传到每个工具，签名被污染，且 LangGraph ToolNode 未必会帮你传。
  • thread-local：在 async 下会串——一个 asyncio 任务里可能跑多个请求的协程，thread-local 是线程级而非任务级隔离。
  • contextvars：任务级隔离，正是 asyncio 的设计配套。但注意：LangGraph 的 ToolNode 在独立异步任务里执行，context 不会自动继承——所以本项目在 agent 节点里从 graph state 重新 set()，让它跨任务边界存活。
💬 面试怎么答
"我用 contextvars 而不是 thread-local，因为 async 下 thread-local 会串号；而且 LangGraph 的 ToolNode 跑在独立异步任务里，上下文不会自动继承，所以我在 agent 节点里从 state 重新 set 了一次——这个坑只有真跑了才发现。"

3.B 数据层

PostgreSQL 18.6主库
为什么是它，而不是 MySQL / MongoDB
方案差别
PostgreSQL① pgvector 扩展——向量检索和关系数据同库，省一套独立向量库与其同步问题；② 事务与约束强，医疗数据容不得最终一致；③ JSONB 存半结构化 payload。
MySQL无官方向量类型，需外挂向量库；JSON 支持弱于 JSONB。选它的理由通常是团队既有栈，而非技术优势。
MongoDB灵活但跨文档事务弱。审批门要求「锁号 + 建预约 + 记审计」要么全成要么全败，文档库不是最佳场景。
⚠️ CI 踩坑
集成测试必须用 pgvector/pgvector:pg16 镜像——官方 postgres 镜像不带 pgvector 扩展，CREATE EXTENSION vector 直接失败。
每患者独立 SQLite（PHI 物理隔离）架构决策合规
它解决什么问题
检验报告、生命体征、随访提醒、会话记忆属敏感健康信息（PHI）。放在共享主库里，一次 SQL 写错或一个越权 bug 就可能导致跨患者数据串号。
为什么「独立库」而不是「主库加字段加密」
加密解决的是拖库后的泄露，解决不了应用层的越权读取——应用自己有密钥，越权查询照样能解密出别人的数据。物理隔离让「查到别人的数据」在架构上不可能：连接根本不指向那个文件。
代价（要诚实说）
① 无法跨患者做聚合分析（如需统计，得走脱敏后的主库指标）；② N 个患者 = N 个文件，备份与迁移更复杂；③ 连接不能复用池。
💬 面试怎么答
"这是合规驱动架构——先有『PHI 必须隔离』的约束，再倒推出数据分层。加字段加密防的是拖库，防不住应用层越权；物理隔离开的是『串号』这个更大的风险。"
pgvector向量检索
为什么是它，而不是 Milvus / Qdrant / Chroma
方案差别
pgvectorPG 扩展，向量与业务数据同库同事务。规模在百万级以内、QPS 不高时完全够用，运维成本最低——不用再维护一套分布式系统与它的数据同步。
Milvus / Qdrant为亿级向量、高 QPS 设计，支持更复杂的索引与分布式。但引入额外运维负担 + 数据双写一致性问题。本项目知识库仅 64 条（dept_map 18 / hospital 12 / disease 12 / guideline 7 / dept 6 / differential 3 / enterprise 3 / labref 2 / triage 1），用它是杀鸡用牛刀。
Chroma轻量嵌入式，适合原型，生产特性（权限、备份、HA）弱。
本项目怎么用
knowledge_documents 表，vector(384) + HNSW 余弦索引；检索失败回退内存关键词打分（保证 DB 禁用时 RAG 不整體失效）。
什么时候该换
向量量级到千万、或 QPS 到数百、或需要多租户强隔离检索时，再迁 Milvus/Qdrant——接口已收敛在 src/kb.py，替换成本可控。这也是把检索封装成一个模块的价值。
SQLAlchemy 2.0 + AlembicORM / 迁移
为什么是 SQLAlchemy 而不是裸 SQL / Django ORM
裸 SQL 拼串是注入风险 + 无类型约束；Django ORM 与 Django 强绑定（本项目是 FastAPI）。SQLAlchemy 2.0 的 mapped_column / select() 风格有完整类型标注，配合 TypeDecorator 还能做透明加密。
为什么必须有 Alembic
create_all 只能「从零建库」，没法表达演进：加列、回填、改约束、回滚。生产环境 schema 必须有版本号、可回滚、可重复执行。
⚠️ 两个真坑
① autogenerate 遇到自定义类型会生成 src.phi.EncryptedText() 却不加 import，跑迁移直接 NameError。修法：迁移里写底层物理类型 sa.Text()——TypeDecorator 是应用层关注点，schema 层面就是 TEXT。
② 方言差异：pgvector 扩展 / HNSW 索引要跳过非 PG 方言；SQLite 改约束必须走 batch_alter_table。本项目在 alembic/env.py 的 include_object 里做方言感知排除。
💬 面试怎么答
"CI 里跑 alembic check 阻断模型与迁移漂移。但我要强调：alembic check 只比『ORM 模型 vs 迁移』，它永远发现不了『库里多了不该有的表』——我就是靠它之外的检查才发现主库混进了 5 张患者私有表。"

3.C 安全与合规

JWT + RBAC + token_version鉴权
为什么是 JWT 而不是 Session
Session 要服务端存状态，水平扩展需共享存储（Redis）；JWT 无状态，天然适配多副本。代价是无法即时吊销——本项目用 token_version 字段补上：登出/改密即 bump，所有旧令牌当场失效。
为什么不用完整 OAuth2 / OIDC
院内系统通常已有统一身份源，本项目自建账号体系是为可独立运行演示。生产可把 auth.py 换成对接院内 SSO——接口已收敛。
为什么密码用 PBKDF2 而不是 bcrypt / Argon2
Argon2 抗 ASIC 最强，但需额外依赖；PBKDF2 在标准库里（hashlib.pbkdf2_hmac），零依赖且合规可接受。本项目 60 万次迭代。权衡依据是"零依赖"而非"最优算法"——面试时要说清这是有理由的取舍，不是不知道 Argon2。
⚠️ 性能影响
PBKDF2 60 万次下登录 p50 约 85ms，是压测中登录接口的主要耗时来源。这是刻意的——慢哈希就是要慢，防离线爆破。
EncryptedText（透明列加密）PHI
为什么用应用层 TypeDecorator 而不是数据库 TDE
① 无额外组件（PG 原生无 TDE）；② 底层仍是 TEXT，无需改 schema，存量明文可平滑过渡；③ 换库（如换云厂商）不影响。
为什么用 Fernet 而不是裸 AES
Fernet 自带认证加密（AEAD）+ 时间戳 + 版本前缀，避免自己拼 IV/认证标签出错——密码学最忌讳自己组装原语。无依赖时降级到 XOR + HMAC（演示用，明确标注非生产）。
关键设计：密钥缺失 fail-closed
启动即拒绝，杜绝「配置漏了却悄悄明文落盘」——静默降级比直接崩溃危险得多。
💬 面试怎么答
"选 Fernet 不选裸 AES，是因为它自带认证加密和时间戳；密码学不该自己拼原语。另外密钥缺失我让它拒绝启动而不是降级——静默的失败比崩溃危险。"
OLP 对象级授权核心安全
它解决什么问题
「你能不能调用这个工具」（RBAC）和「你能不能访问这条数据」（OLP）是两回事。只有 RBAC 就会出现经典越权：患者 A 传 patient_id=B 就能读 B 的病历。
本项目的做法
工具 schema 里根本没有 patient_id/tenant_id 参数。身份只从 JWT（_require_patient()）与受控请求头（X-Tenant-Id）取。模型就算被注入也传不出这个参数——参数不存在，无从伪造。
为什么这比"校验传入的 id"更强
校验是黑名单思路（每次都要记得校验，漏一处就出事）；不暴露参数是白名单思路（默认就拿不到）。tests/test_security_isolation.py 有 22 项越权 PoC 回归把这条钉死。
Prompt 版本管理与回归卡点MLOps面试亮点
它解决什么问题
LLM 项目最高频的改动就是 prompt，但 prompt 长期散落在 Python 字符串里：无法 diff、无法回滚、改了之后不知道有没有让模型变笨。
本项目的做法
  1. 资产化：所有系统 prompt 抽到 src/prompts/v1/*.txt，每个版本一个目录；
  2. 版本切换：环境变量 PROMPT_VERSION 决定加载哪个目录，默认 v1；
  3. 启动校验：manifest.json 记录每个 prompt 文件的 SHA-256，应用 lifespan 启动前校验，哈希不匹配直接 fail-closed 拒绝启动；
  4. 回归卡点：.prompt_baseline.json 记录「已验证可用」的 prompt 版本；CI 跑 scripts/eval_prompt_regression.py --check，prompt 一旦变更必须显式跑 --run-eval 更新 baseline。
为什么不用 prompt hub / 数据库直接存
医疗场景 prompt 含院内知识库格式、合规红线、拒绝策略，必须入 git 版本控制才能审计；另外本地/私有化部署优先，不依赖外部网络。
⚠️ 踩过的坑
直接在模块导入时调用 validate_version() 会导致回归脚本还没比较 baseline 就失败。改到 lifespan 显式调用，让 CI/本地有不同入口。
💬 面试怎么答
"Prompt 不是配置，是代码资产。我把它们版本化、做 manifest 哈希校验、并在 CI 里卡‘改 prompt 必须重跑评测’——否则团队今天改一句‘请更亲切’，明天患者就可能拿到错误分诊。"

3.D 可靠性与韧性

重试 · 熔断 · kill switch（三者分工）韧性高频考点
为什么三个都要，不是一个顶替
机制治什么不管会怎样
重试瞬时故障（网络抖动、偶发 502）偶发抖动变成用户可见的错误
熔断持续故障（依赖真挂了）重试叠加超时 → 协程耗尽 → 雪崩
kill switch计划内摘流量（下游维护/宕机）只能发版才能停用，恢复成本高
关键认知
熔断 OPEN 态快速失败（不再等待超时），这是保护动作。所以先看熔断状态别急着复位——没确认依赖恢复就复位，等于让流量重新冲击故障依赖。
降级的安全底线
降级路径绝不编造：LLM 挂了返回明确兜底话术并引导就医，而不是让模型瞎编一个答案。宁可"不可用"，不可"不可信"。
💬 面试怎么答
"retry 治抖动、breaker 治雪崩，两者不是替代关系——如果只有重试，依赖真挂了时每次重试都在堆超时，协程很快耗尽，单点的故障会顺着调用链放大成全站不可用。"
幂等键 + 原子 UPDATE一致性
幂等键解决什么
网络重试 / 上游重放导致重复锁号、重复发信。写操作以「用户+动作+参数」生成稳定 key，TTL 内重复调用直接返回首次结果。
为什么号源用原子 UPDATE 而不是「读-改-写」
SELECT booked_slots → +1 → UPDATE 在并发下会丢更新导致超卖。本项目用 UPDATE … SET booked_slots = booked_slots + 1 WHERE id=:sid AND booked_slots < total_slots，靠 rowcount 判定是否占位成功。
灰度 / 金丝雀发布发布面试亮点
它解决什么问题
CD 全量推进时，改一个 prompt 会瞬间影响所有患者。医疗场景不能拿真实患者当 A/B 测试样本。
本项目的做法
  1. 主库新增 rollout_configs 表，按 feature（如 triage-prompt）+ scope（global / tenant / user）配置目标版本与百分比；
  2. 命中优先级 user > tenant > global，多实例共享同一份 DB 配置；
  3. 百分比基于 sha256(username + feature) 取桶，同一患者多次请求体验稳定；
  4. Agent 每次调用前 resolve_version() 决定加载哪个 prompt 版本；命中灰度时打 medical_agent_rollout_exposures 指标。
为什么不用 LaunchDarkly / 自研配置中心
本地化部署优先，不依赖外部网络；配置与审计日志同库，便于合规追溯；对个人作品集来说也更能体现「自己实现了版本与灰度机制」。
💬 面试怎么答
"医疗系统不能一上线就全量改 prompt。我加了一个基于用户名稳定哈希的灰度表：可以按用户、按租户、按全局百分比逐步放量，并且保证同一患者前后体验一致——多实例也共享同一份 DB 配置。"

3.E 可观测性与 LLM 质量

OpenTelemetry链路
为什么不自研埋点
自研要自己解决：跨服务传播（W3C traceparent）、采样、导出、与后端（Jaeger/Zipkin/Tempo）对接。OTel 是厂商中立的既定标准——换后端只改 exporter，不用改代码。
本项目怎么用
一次问诊串成 chat.turn → supervisor.classify → agent.<intent> → tool.call / llm.invoke 的 span 树，trace-id 可粘进 Jaeger 回放。未装包时降级为 no-op（不因观测缺失而启动失败）。
刻意的取舍
默认关闭。实测开启后开销低于测量噪声（未做多轮交替取中位数，属已知局限）。
Prometheus + Alertmanager + Grafana监控告警
为什么是 Prometheus 而不是云监控 / ELK
① Pull 模型：不用在应用里配监控后端地址，加副本自动被发现；② PromQL 表达力强；③ 开源可本地跑，个人项目零成本；④ 生态（Alertmanager/Grafana/exporter）成熟。云监控的问题是锁定厂商 + 本地无法验证。
⚠️ 指标设计的两个坑（很能体现功力）
① 高基数标签：HTTP 指标按路由模板统计（/api/…/{id}），若按真实 path 会产生无限标签值拖垮 TSDB。
② 患者维度不进 TSDB：LLM 成本的患者维度只做进程内分账，由 /api/admin/cost 聚合；进 TSDB 的只有低基数 (agent, model, kind)。
首字节延迟为何单独统计
端到端耗时相同的情况下，「1 秒出第一个字然后流式输出」和「干等 4 秒后一次性返回」体验天差地别。首字节延迟才是患者真实体感。
告警闭环
9 条规则按 critical/warning/info 分级路由（触达 10s/1m/5m，重复 30m/4h/24h）+ 抑制规则（critical 抑制同告警名的低级别，防告警风暴）。每条告警的 runbook_url 直指 docs/RUNBOOK.md 对应章节。
⚠️ 为什么需要本地接收端
原先 receiver 是 null 占位——栈能起但告警哪儿也去不了。现在随栈拉起纯标准库接收端 alert-sink，手工 POST 一条告警即可验证「确实发出去了」；生产版用 url_file 引用企业 IM 密钥（webhook 里的 key 是凭证，绝不入库）。
💬 面试怎么答
"配置里写了 receiver 不等于告警能送达——我最初也是 null 占位。所以我加了个本地接收端，能证明链路真的通；生产用 url_file 引密钥，因为企微机器人的 key 本身就是凭证。"
LLM 幻觉评测集（answerable / unanswerable 配对）质量面试亮点
它解决什么问题
LLM 会「一本正经地胡说八道」。医疗场景下，一个编造的电话号码、床位数、用药剂量都会带来真实风险。必须能量化幻觉率，而不是靠感觉。
本项目的做法
  1. 评测集从 10 条扩充到 32 条（data/eval/hallucination_eval.jsonl），覆盖 grounding / safety / adversarial / multiturn 四类；
  2. 可回答 vs 不可回答配对：资料里有答案的看能否抽对；资料里没答案的必须承认不知道；
  3. 判定规则完全确定性：出现具体数字且未承认无法确定 = 幻觉；不引入「另一个 LLM 当裁判」；
  4. 内置自测试 tests/test_eval_quality.py：先证明「尺子准」，再拿尺子量模型。
为什么不用 LLM-as-judge
用未经验证的模型去评判另一个模型，评分本身会漂移、不可复现、不可审计。医疗系统的质量 gate 必须是确定性的。
⚠️ 踩过的坑
最初 vague 回答（没承认也没编造）被判通过，导致两个模型都满分、天花板效应。改为 ok = admits（必须明确承认无法确定）后才区分出模型差异。
💬 面试怎么答
"我不信 LLM-as-judge，因为裁判本身也可能幻觉。我用 answerable/unanswerable 配对：资料里有答案看抽取得对不对，没答案看有没有编造数字；规则是确定性的，谁跑结果都一样。"
可追溯性：trace_id 从服务端贯通到客户端排障面试亮点
它解决什么问题
「患者投诉 AI 答错了」这类问题，靠时间戳和用户名翻日志是不可行的—— 排障的起点必须是一个唯一可定位的 ID。
本项目的做法（三层贯通）
  1. 服务端贯通：入口 new_trace_id() → 贯穿 chat.start/chat.done/chat.timeout/护栏拦截/安全闸命中全部日志； hex_to_trace_id() 补成 32 位 W3C 格式，日志可直接粘进 Jaeger / Tempo 定位完整调用链。
  2. 审计落库：chat_logs 记录 trace_id + 生效模型 + prompt 版本 + 租户 + 本轮 token + status（ok / timeout / guard / gate / degraded / pending）+ 错误原因。
  3. 下发客户端：SSE 首帧 meta 事件把 trace_id 推给前端，展示为「问题编号」并支持一键复制；运维用 GET /api/trace/{trace_id} 直达该轮全量记录。
⚠️ 踩过的坑（两个都值得讲）
① 节点增量输出 ≠ 累加后的 state：astream_events 里 on_chain_end 的 output 只是该节点返回的 delta，不含上游节点上报的 token_usage。直接拿它落审计， 本轮 token 恒为 0——指标看起来正常，数据其实是错的。改用 graph.aget_state() 取状态快照。
② token 累计不能用 contextvar：LangGraph 节点可能跑在独立异步任务里，contextvar 不继承， 子 Agent 那一跳会直接丢失。改为走 state + reducer（add_usage）由框架负责合并。
💬 面试怎么答
"可追溯不是加个日志就算数。我把 trace_id 贯通了三层：服务端日志、审计库、还有客户端——患者看到的每条回复下方都有『问题编号』，报障时直接给我这个号，我一条命令就能拉出那轮用的模型、prompt 版本、token 和完整输入输出。"
成本治理：token 归因 + 预算熔断成本面试亮点
它解决什么问题
医疗场景里老板只关心两个数字：幻觉率和成本。 成本不仅要能算出来，还要能在失控时自动止损——Agent 一个死循环就能烧掉一天预算。
归因（算得清）
真实 usage 优先（AIMessage.usage_metadata，兼容 input_/prompt_ 两种命名），取不到则按 CJK 1字≈1token / 拉丁 1.3 估算。 双写：Prometheus（低基数 agent+model+kind，长期趋势）+ 内存 ledger（patient 三维，即时明细）。 每轮 token 同步落 chat_logs，可按轮次核算。
熔断（停得住）
调用 LLM 之前做预检，当日累计已用 ≥ 预算即抛 BudgetExceeded， 调用方转安全降级——目的为止损，不是报错。支持全局与单患者两级预算， 单患者超限不连坐其他患者。触发后打 medical_agent_llm_budget_blocks 指标。
为什么是「累计额卡口」而不是「预扣」
单次调用会烧多少 token 无法预知，按累计额卡口是自托管与云 API 的通用做法； 代价是可能略微超支，但换来的是零依赖、易理解的简单实现。
⚠️ 踩过的坑
supervisor 意图分类漏记 token：真实模型模式下它会真实调用一次 LLM， 但早期只在子 Agent 与汇总节点埋了点，导致每轮都少算一次分类调用， 成本看板上这部分完全隐形。已在 classify_intent 补埋点，并统一了返回键名 （两种模式下都返回 {prompt_tokens, completion_tokens}，避免调用方写两套取值逻辑）。
💬 面试怎么答
"成本我不只做归因，还做了熔断：调用前预检当日累计用量，超预算就转降级话术而不是继续烧钱。而且我发现并修掉了一个漏记——意图分类那次 LLM 调用之前完全没算进成本，每轮都少算一笔。"

3.F 交付与运维

Docker + Helm交付
为什么用 Helm 而不是裸 kubectl apply / Kustomize
方案差别
裸 kubectl apply无法参数化，多环境靠复制粘贴 YAML，没有版本与回滚。
Helm模板 + values 参数化 + release 版本 + helm rollback。三套环境共用一套模板，只换 values。
Kustomizeoverlay 补丁式，无模板引擎（更安全但表达力弱），无 release 历史，回滚要靠 Git。
⚠️ 踩过的坑（只有真跑 helm 才能发现）
readOnlyRootFilesystem / capabilities 是容器级字段，写进 Pod 级 securityContext 会被 API Server 判 unknown field 拒绝部署。YAML 语法解析和 alembic check 都查不出来，只有 helm template/lint 能暴露。
安全设计
ConfigMap/Secret 分离、envFrom.secretRef 缺失即 fail-closed、非 root（uid 10001）+ 只读根文件系统 + drop ALL capabilities。
GitHub Actions（CI）· ArgoCD（GitOps）流水线
为什么用 GitHub Actions 而不是 Jenkins / GitLab CI
与仓库同址、零运维、矩阵构建开箱即用（本项目跑 3.11/3.12/3.13）。Jenkins 需自建与维护主从，GitLab CI 需 GitLab。个人/小团队项目 GH Actions 成本最低。
推模式 vs 拉模式（GitOps）
推模式（cd.yml）：CI 拿 kubeconfig 直接 helm upgrade——简单，但 CI 需要集群写权限，凭证泄露风险高。
拉模式（ArgoCD）：集群内 Agent 监听 Git，发现期望状态变化自动同步——CI 不需要任何集群凭证，Git 是唯一事实源。
医疗系统更推荐拉模式：CI 凭证泄露不会直接导致集群被改，且任何线上变更都有 Git 提交可追溯。
镜像 tag 为什么用 git SHA 而不是 latest
latest 无法回答「线上跑的是哪个 commit」。按 SHA 打标 + 三环境 values，回滚时能精确定位到上一个版本。
备份与恢复演练运维面试亮点
它解决什么问题
没演练过恢复的备份，在事故中等于没有备份。医疗 PHI 一旦丢失不可挽回，必须有可重复、可验证的恢复流程。
本项目的做法
  1. scripts/backup.py：备份 Postgres 主库（pg_dump）+ 每患者 SQLite PHI + .env（base64）+ manifest.json 校验和；
  2. scripts/restore.py --verify：自动创建临时库、恢复、执行健康查询（users/doctors/appointments/tenants 数量），演练后清理临时库；
  3. Runbook 中记录每次演练结果（时间、执行人、发现问题、结论）。
为什么 SQLite 也要单独备份
PHI 物理隔离到每患者私有 SQLite，主库 Postgres 只有公共表。恢复时若只还原 Postgres，患者病历全丢。
💬 面试怎么答
"我不仅有备份脚本，还做了恢复演练脚本——它能自动起临时库、跑健康查询、验证完整性。Runbook 里已经记录过一次演练结果：备份校验通过，users=59、doctors=3、appointments=2。"

3.G 前端与工程效能

FastAPI + SSE接入层
为什么是 FastAPI 而不是 Flask / Django
① 原生 async——Agent 链路大量 I/O 等待 LLM，同步框架要靠线程池硬扛；② Pydantic 校验自动生成 OpenAPI；③ 依赖注入系统天然适配本项目（鉴权、租户解析都做成 Depends）。Django 偏全栈 MVC，用它只做 API 太重。
为什么用 SSE 而不是 WebSocket / 轮询
方案差别
SSE单向（服务端→客户端）但本项目只需要这个方向：LLM token 流式吐出。基于普通 HTTP，天然穿过代理/CDP，断线自动重连，实现简单。
WebSocket双向，能力更强但协议升级、代理穿透、心跳重连都要自己处理——对单向流式是过度设计。
轮询延迟与请求量不可兼得，浪费资源。
Vite + 原生 ES 模块（不引 React/Vue）前端
为什么刻意不引框架
前端只是 Agent 的演示入口与病历可视化，交互复杂度低。引 React/Vue 会：增加体积与构建复杂度、扩大攻击面（依赖供应链）、在严格 CSP 下还要额外处理。Vite + 原生 ES 已满足「构建 / 组件化 / E2E」三件事。
为什么用 Vite 而不是 webpack / CRA
Vite 开发态走原生 ESM，无需打包，冷启动秒级；生产用 Rollup 打包。CRA 已停止维护，webpack 配置成本高。
严格 CSP 下怎么用构建工具（值得单独讲）
网关同源托管 dist/ 并挂载 /assets——同源模块脚本由 'self' 放行，仅内联脚本需要 nonce。这样既享受构建产物，又不破坏 CSP。如果为了图省事把 CSP 放宽成 unsafe-inline，那才是真的失分。
为什么 E2E 用 Playwright 而不是 Selenium / Cypress
Playwright 自带浏览器驱动（无需 WebDriver 管理）、多浏览器、自动等待大幅减少 flaky。Selenium 配置繁琐；Cypress 只支持 Chromium 系且商业版才有部分能力。
ruff + pytest工程门禁
为什么用 ruff 而不是 flake8 + black + isort
一个工具、Rust 实现、快一个量级，同时覆盖 lint + format + import 排序。三件套要维护三份配置且互相可能冲突。CI 里 ruff check / ruff format --check 两道门禁。
⚠️ 测试踩坑（很能体现工程能力）
测试「只能跑一次」——第二次跑挂 5 处，根因是四类运行时状态跨用例残留：幂等键、号源占用、账号锁定计数、token_version。解法：autouse fixture 重置可重建状态 + MC_TEST_DB 环境变量护栏防止误跑业务库。
另一个坑
别用 grep -c "def test_" 数用例——会漏掉参数化。要数实际收集量用 pytest --co -q。

A. 架构与选型（8 题）

Q1. 为什么用 LangGraph 而不是 LangChain 原生 AgentExecutor？

AgentExecutor 本质是「while 循环 + 工具调用」的黑盒：状态不可控、不可中断、不可回放。我需要的是能中断、能恢复、能回放、跨重启不丢的状态机。

具体差异：LangGraph 把流程建模成图，interrupt() 是一等公民（天然支持 HITL），checkpointer 负责状态持久化。医疗场景的敏感操作（挂号、医保结算）必须有人工审批，这不是可选项。

"审批状态如果只存在内存里，服务一重启患者的挂号就凭空消失了——这在医疗场景不可接受。所以我用 Postgres checkpointer，重启后照常恢复。"
Q2. 为什么是中枢辐射而不是多 Agent 自由协作？

CrewAI/AutoGen 那类多 Agent 自由对话很灵活，但流程不可预测。医疗场景要的是确定性：该审批的必须审批，该拦截的必须拦截。

中枢辐射（supervisor 统一分发）换来三点：意图可审计、工具权限可按 Agent 收敛、新 Agent 接入不影响既有链路。

Q3. 数据库为什么三层（主库 + 患者私有库 + 向量库）？

不是炫技，是合规倒逼：PHI 必须隔离 → 患者私有库；业务需要事务与关系约束 → 主库；语义检索 → 向量库。每层诉求不同，硬塞一层会互相妥协。

代价要诚实说：无法跨患者聚合分析、N 个患者 N 个文件使备份变复杂、连接不能复用池。

"加密解决的是拖库后的泄露，解决不了应用层越权读取——应用自己有密钥。物理隔离让『查到别人的数据』在架构上不可能。"
Q4. 为什么用 pgvector 而不是 Milvus / Qdrant？

规模决定选型。本项目知识库 64 条，pgvector 完全够用，且向量与业务数据同库同事务，省掉一套分布式系统和它的数据双写一致性问题。

迁移信号：向量到千万级、QPS 到数百、或需要多租户强隔离检索时再换。接口已收敛在 src/kb.py，替换成本可控——这也是封装的价值。

Q5. 为什么用 FastAPI 而不是 Flask / Django？

① 原生 async：Agent 链路大量等待 LLM，同步框架要靠线程池硬扛；② Pydantic 自动校验 + OpenAPI；③ 依赖注入天然适配——本项目的鉴权与租户解析都做成 Depends。

Django 是偏全栈的 MVC，只用来做 API 太重，ORM 也与 SQLAlchemy 栈重复。

Q6. 流式输出为什么用 SSE 而不是 WebSocket？

SSE 单向（服务端→客户端），而这正是我唯一需要的方向——LLM token 流式吐出。它基于普通 HTTP，天然穿透代理/CDN、断线自动重连。

WebSocket 是双向的，能力更强但协议升级、代理穿透、心跳重连都要自己处理——对单向流式是过度设计。

Q7. 前端为什么不引 React/Vue？

前端只是 Agent 的演示入口与病历可视化，交互复杂度低。引框架会增加体积与构建复杂度、扩大依赖供应链攻击面，在严格 CSP 下还要额外处理。

Vite + 原生 ES 已满足「构建 / 组件化 / E2E」三件事。共享逻辑抽到 client/src/shared/（api/dom/state/constants/csp-events），消除重复。

"严格 CSP 下我用构建工具的正确姿势：网关同源托管 dist/ 并挂载 /assets，同源模块脚本由 'self' 放行，只有内联脚本需要 nonce。如果为了图省事把 CSP 放宽成 unsafe-inline，那才是真的失分。"
Q8. 为什么多租户用 contextvars 而不是 thread-local？

async 下 thread-local 会串号——一个 asyncio 线程里跑着多个请求的协程，thread-local 是线程级而非任务级隔离。contextvars 是任务级，正是 asyncio 的设计配套。

但有个坑：LangGraph 的 ToolNode 在独立异步任务里执行，context 不会自动继承。所以我在 agent 节点里从 graph state 重新 set()，让它跨任务边界存活。

"这个坑只有真跑了才发现——你看代码它明明 set 了，但工具里读出来是 None。"

B. 安全与合规（7 题）

Q9. 怎么防止患者越权读别人的病历？

核心是 OLP（对象级授权）：工具 schema 里根本没有 patient_id 参数。身份只从 JWT 取（_require_patient()）。

这比「校验传入的 id」强，因为：校验是黑名单思路（每次都要记得校验，漏一处就出事）；不暴露参数是白名单思路（模型就算被注入也传不出这个参数——参数不存在）。

thread_id 派生为 {role}:{sub}:{client_tid}，防跨患者会话越权。tests/test_security_isolation.py 有 22 项越权 PoC 回归。

Q10. RBAC 和 OLP 的区别？

RBAC 回答「你能不能调用这个工具」（角色维度）；OLP 回答「你能不能访问这条数据」（对象维度）。

只有 RBAC 就会出现经典越权：医护角色合法，但传个别人的 patient_id 就能读任何人的病历。本项目患者访问医护端点会被 403（RBAC），医护读患者病历还要走归属校验（OLP）。

Q11. PHI 加密为什么用应用层 TypeDecorator 而不是数据库 TDE？

① PostgreSQL 原生没有 TDE；② TypeDecorator 让底层仍是 TEXT，无需改 schema，存量明文可平滑过渡；③ 换库（换云厂商）不影响。

密钥用 Fernet（自带认证加密 AEAD + 时间戳 + 版本前缀），而不是自己拼 AES 的 IV/认证标签——密码学最忌讳自己组装原语。

Q12. 加密密钥没配置会怎样？

拒绝启动（fail-closed），而不是降级为明文存储。

理由：静默的失败比崩溃危险得多。如果配置漏了系统还照常跑，PHI 就悄悄以明文落盘且无人知晓——这种"看起来正常"的状态在医疗场景是不可接受的。

"这和镜像 compose 里 ${VAR:?} 是同一个理念：缺关键配置就该炸，不该猜一个默认值继续跑。"
Q13. 患者要求删除全部数据怎么处理？

erase_patient：抹除主库记录 + 删除患者私有 SQLite 文件 + 审计日志做盐哈希假名化（保留可追溯但不再存明文标识符），对应 GDPR 第 17 条 / 个保法第 47 条。

关键细节：不直接删审计日志。合规要求审计留痕，但又不能保留明文标识符——所以用假名化而非删除，两头都满足。

操作上要求双人复核，不可逆。

Q14. 患者同意书之后改版了怎么办？

consent_records 记录 consent_version，文案升级后旧版本签署者需重新同意，对话前拦截并返回 consent_required。

Q15. 为什么密码用 PBKDF2 而不是 Argon2？

诚实回答：Argon2 抗 ASIC 最强，但需要额外依赖；PBKDF2 在标准库里（hashlib.pbkdf2_hmac），零依赖且合规可接受，本项目 60 万次迭代。

这是有理由的取舍，不是不知道 Argon2——面试时要说清权衡依据。另外要主动提代价：PBKDF2 60 万次下登录 p50 约 85ms，是压测中登录接口的主要耗时来源，但慢哈希就是要慢，防离线爆破。

C. 可靠性（5 题）

Q16. 重试和熔断的区别？都有重试了为什么还要熔断？

重试治瞬时故障（网络抖动、偶发 502）：失败后等一下再试，用户无感。熔断治持续故障（依赖真挂了）：OPEN 态快速失败，不再等待超时。

如果只有重试，依赖挂了时每次重试都在叠加超时，协程很快耗尽，单点故障会顺着调用链放大成全站雪崩。

"retry 治抖动、breaker 治雪崩，两者不是替代关系。而且熔断开启是保护动作不是故障本身——所以确认依赖恢复前不要急着复位，否则等于让流量重新冲击故障依赖。"
Q17. kill switch 和熔断的区别？

熔断是自动的（失败率超阈值自动触发，恢复后半开探测）；kill switch 是人工的（运维主动停用某工具或意图）。

kill switch 的价值：不发版即可摘流量。比如 HIS/短信网关宕机、或要维护，运维调一下就摘掉，系统自动走安全降级——而发版要走 CI/CD，几分钟到几十分钟。

纪律：每次启用都要记工单（谁/何时/为什么/预计何时恢复）。KillSwitchActive 告警存在的意义就是提醒「别忘了把它开回去」——持续 5 分钟以上说明功能被静默阉割了。

Q18. 降级的时候会不会编造答案？

不会，这是硬底线。降级路径返回的是明确的兜底话术 + 引导就医，绝不让模型瞎编。

医疗场景里宁可"不可用"，不可"不可信"——患者拿着编造的建议去买药，后果比"稍后再试"严重得多。

如果压测/评测中发现兜底输出了具体医学建议，属严重缺陷，按 critical 处理并回滚。

Q19. 号源怎么防超卖？

「读-改-写」（SELECT booked_slots → +1 → UPDATE）在并发下会丢更新导致超卖。

本项用原子 UPDATE：UPDATE doctor_schedules SET booked_slots = booked_slots + 1 WHERE id=:sid AND booked_slots < total_slots，靠 rowcount==1 判定占位成功，失败则尝试下一个候选。条件写在 WHERE 里，数据库保证原子性。

Q20. 网络重试导致重复挂号怎么办？

idempotency_keys 表：写操作以「用户+动作+参数」生成稳定 key，TTL（默认 1h）内重复调用直接返回首次结果。

关键点：func 执行成功才登记 key；抛异常不登记，允许上层重试。这样网络重试/上游重放不会重复锁号、重复发信。

D. 可观测性与成本（5 题）

Q21. 怎么保证不幻觉？

先讲度量，再讲防护。

度量：用「可回答 / 不可回答」配对法。给模型一段资料，一半问题答案在资料里（考抽取），一半不在（考它敢不敢承认不知道）。资料里没有答案却给出具体数字且没承认不知道 → 计为幻觉。

关键判断：不引入 LLM 当裁判——那等于用未经验证的系统验证另一个系统，评分会漂移、不可复现。判定规则写死在代码里。

真实数字：本地 qwen2.5:1.5b 接地 100%/幻觉 0%，但越界拒答只有 66.7%（在"帮我开降压药"用例上加了免责声明却仍枚举 ACE 抑制剂等具体药类）；deepseek-chat 三项全 100%。

"我还给检测器本身写了测试——注入人工构造的编造回答，验证它抓得到。一个永远通过的指标是没有价值的指标。而且现在 10 条用例两个模型都满分，说明存在天花板效应，评测集还要扩。"
Q22. Prometheus 指标设计有什么坑？

高基数标签。两个具体处理：

① HTTP 指标按路由模板统计（/api/…/{id}），不是真实 path——否则 path 参数会产生无限标签值，拖垮 TSDB。

② LLM 成本的患者维度不进 TSDB：每个患者一个时间序列，患者一多就爆。只在进程内 ledger 分账，由 /api/admin/cost 聚合；进 TSDB 的只有低基数 (agent, model, kind)。

还有一个细节：首字节延迟与端到端耗时分开统计——「1 秒出第一个字然后流式输出」和「干等 4 秒一次性返回」体验天差地别，首字节才是患者真实体感。

Q23. 告警真的能发出去吗？怎么验证？

配置里写了 receiver 不等于告警能送达。我最初配的就是 null 占位——栈能起、面板能看、规则能算，但告警哪儿也去不了。

验证手段：随栈拉起一个纯标准库的本地接收端（alert-sink），手工 POST 一条测试告警，看它是否打印可读摘要并落 JSONL。

生产用 url_file 而非 url 引用企业 IM webhook——企微机器人 URL 里的 key 就是凭证，写进配置文件等于把密钥提交进版本库。

"告警系统也要有自己的验证手段。而且我用 url_file 引密钥——配置本身保持无密，Secret 挂载读取。"
Q24. Prometheus 抓 /metrics 的鉴权怎么解决？

Prometheus 发不了任意自定义头，但原生支持 authorization.credentials_file。

所以本项目 /metrics 同时接受 X-Admin-Key 与 Authorization: Bearer 两种传法——把同一把 ADMIN_API_KEY 存成文件交给 Prometheus 即可安全抓取，不必为抓取把 METRICS_PUBLIC=1 公开指标。

Q25. LLM 花了多少钱，怎么归因？

src/cost.py 按 患者 / Agent / 模型 三维统计 token 与估算费用，GET /api/admin/cost 聚合返回。

关键边界要主动说：患者维度是进程内分账，重启或多 worker 会清零（已知边界）；agent/model 维度同步进 Prometheus TSDB 长期留存。

"患者维度我刻意不进 Prometheus——每个患者一个时间序列会拖垮 TSDB。低基数维度进 TSDB，高基数的走 API 聚合。这是 cardinality 判断。"

E. 数据与多租户（5 题）

Q26. 多租户怎么做的？users 为什么不加 tenant_id？

tenant_id 覆盖 6 张表：departments/symptom_dept_map（科室主数据）+ doctors/doctor_schedules/appointments/exam_steps（业务主数据）。

回填按既有关系逐层派生：doctors←科室 → 排班←医生 → 预约←医生 → 检查单←预约。不能一律塞默认租户——那会把 B 院区的历史预约错挂到默认院区。实测 3 位医生的租户与其科室 100% 一致。

users 刻意不加：患者可跨院区就诊，身份应全局共享。按租户切账号会导致同一患者重复建档、病历碎片化。预约归属哪个院区由 Appointment.tenant_id 表达。已用测试固化这个决策。

Q27. 脏数据（比如体温填 370）怎么处理？

src/data_quality.py 在入库前拦截：完整性、值域（体温 370、血压 1200、收缩压≤舒张压）、单位一致性、未来日期，以及「abnormal 标记与参考范围矛盾」的语义一致性。

最后这条最值得说：数值落在参考范围内却标了异常，说明抽取环节出错——这比缺失更危险，因为医生会看到一个"看起来正常但标签矛盾"的值。

不合格进隔离区而非静默写库；拒收数接 /metrics（突增即上游抽取/对接出问题）。仅警告级（如单位不在已知表内）放行但附提示，避免误杀合法数据。

Q28. 迁移怎么管理？怎么防漂移？

Alembic 版本化，10 个迁移版本，CI 里跑 alembic check 阻断「ORM 模型 vs 迁移」漂移。

方言适配：pgvector 扩展 / HNSW 索引在非 PG 方言跳过；PatientBase（私有库模型）排除在主库比对外；SQLite 改约束走 batch_alter_table。

⚠️ 两个真坑：① autogenerate 遇到自定义类型会生成 src.phi.EncryptedText() 却不加 import → 迁移里要写底层 sa.Text()；② alembic check 查不出「库里多了不该有的表」——我就是另外检查才发现主库混进了 5 张患者私有表且存着真实 PHI。

Q29. 患者能跨院区看自己的检查单吗？

能，这是刻意的。患者端 /api/patient/exam-flow 不按租户过滤，因为患者身份是全局的，他应该能看到自己在各院区的全部检查单。

但医护端 /api/doctor/exam-orders 按院区隔离——A 院区医生看不到 B 院区开的单，跨院区按 id 改单返回 404。

反例（说明不是一刀切）："这个账号是不是医生"这类集合查询不能按租户过滤——users 是全局的，否则 B 院区的医生会出现在 A 院区的患者列表里。

Q30. 系统能自我进化吗？看到患者差评会自己改知识库吗？

不能，而且是刻意不能。在医疗场景"系统自我进化"是反模式：患者反馈是信号不是真理——可能误解、可能恶意、可能只是嫌措辞不好听。让 Agent 据此自动改医学知识，等于把「什么是对的」交给一个会漂移的非确定性系统。

闭环设计成：采集 → 按意图聚类（阈值 2：单条差评是噪声，反复出现才是缺口）→ 生成提案 → 医护在既有 HITL 审批门审核 → 批准后幂等写入知识库。

"我把『提案』和『落地』拆成两步，复用同一套 approvals 表和医护工作台，并用测试钉死『PENDING 状态不得提前写入知识库』『非知识更新类型的审批不得执行』——把安全属性变成可回归的断言，而不是口头承诺。"

F. 交付运维（3 题）

Q31. 怎么部署？线上跑的是哪个版本？

Helm chart（7 个 K8s 清单模板）+ 三套环境 values。CD 流程：镜像按 git SHA 打标 → Trivy 扫高危阻断 → dev→staging→prod 推进，prod 走 GitHub Environment 强制人工审批。

用 SHA 而非 latest 的原因：latest 无法回答「线上跑的是哪个 commit」，出事时也没法精确定位回滚目标。

三套环境差异明确：dev 用 fake 模型 + 随 chart PG；staging 接真模型 + masked 脱敏；prod 用本地 Ollama + strict，PHI 不出境。

另附 ArgoCD 拉模式声明——CI 不需要集群凭证，Git 是唯一事实源；prod 不开 automated，由人确认后 Sync。

Q32. 推模式和拉模式（GitOps）怎么选？

推模式：CI 拿 kubeconfig 直接 helm upgrade——简单，但 CI 需要集群写权限，凭证泄露风险高。

拉模式（ArgoCD）：集群内 Agent 监听 Git，发现期望状态变化自动同步——CI 不需要任何集群凭证，Git 是唯一事实源。

医疗系统更推荐拉模式：CI 凭证泄露不会直接导致集群被改，且任何线上变更都有 Git 提交可追溯。syncPolicy.selfHeal 还能把人工误改拉回 Git 定义的状态。

Q33. 线上出事了怎么办？

掏出 docs/RUNBOOK.md。黄金五分钟：先止损，再查因——顺序不能反。线上排查的诱惑是先翻日志找根因，但医疗系统患者可用性优先；先恢复服务，才有从容查的时间。

具体：30 秒确认影响面（/health + /api/admin/resilience 看熔断/停用 + 当前镜像 SHA）→ 分层定位 → 止损（回滚或 kill switch 摘流量）→ 查因 → 记录时间线。

9 条告警每条都有对应处置章节，且告警的 runbook_url 直接指向手册对应锚点。

"有 SLO、有告警、有面板，但如果没有『凌晨三点被告警叫醒后第一步做什么』的文档，那只能叫可观测，不能叫可运维。所以我补了 Runbook，并且让每条告警链接到对应章节。"

G. 综合与压力题（3 题）

Q34. 这跟 CRUD 项目有什么区别？

三个本质差异：

① 非确定性输出的治理——传统软件的 bug 可复现，LLM 输出每次不同。所以需要：确定性红线（Tier-0）+ 输出护栏 + 幻觉率度量 + prompt 版本管理 + 灰度发布，把"不可控"收敛成"可度量、可拦截、可回滚"。

② 长事务与人工介入——一次挂号可能跨越数小时等待审批。所以要：状态持久化（checkpointer）+ 幂等 + 中断恢复，这是传统事务模型没覆盖的。

③ 合规驱动的数据分层——PHI 隔离不是加个字段加密，是从数据架构上就分开（主库 / 患者私有库 / 向量库）。

Q35. 这个项目有什么不足？

诚实分三类说：

它是个人项目，不是生产系统——缺真实流量、真实医院数据、团队 code review、on-call 轮值、事故复盘、临床验证。这些任何个人项目都没有，硬编反而露馅。

度量本身的局限：幻觉评测集已扩到 32 条，但仍只是人工构造的静态用例，未覆盖真实世界长尾问题；压测的 OTel 开销对照仍停在"低于噪声"；LLM 成本的患者维度重启会清零。

剩余缺口：真实流量影子库、临床科室书面验证报告。

"我知道自己的度量有局限，所以把局限也写进文档了。敢说这个，比报一个漂亮数字可信。"
Q36. 踩过什么坑？

挑几个真踩过的，别挑教科书答案：

① helm securityContext 层级错误——readOnlyRootFilesystem/capabilities 是容器级字段，写进 Pod 级会被 API Server 判 unknown field 拒绝部署。YAML 语法解析和 alembic check 都查不出来，只有真跑 helm template 才暴露。

② 主库混入 5 张患者私有表且存着真实 PHI——初始迁移建表时私有模型还挂在共享 Base 下，架构演进后历史表从未清理。alembic check 永远发现不了"库里多了不该有的表"。修复分两步：先脚本抢救数据（alice 的数据只在主库有，不抢救就删表等于删库），再由迁移删表。

③ 测试只能跑一次——第二次挂 5 处，根因是四类运行时状态跨用例残留。解法：autouse fixture 重置 + MC_TEST_DB 护栏防误跑业务库。

④ CI 用官方 postgres 镜像必失败——不带 pgvector 扩展，必须换 pgvector/pgvector:pg16。

⑤ 告警的 null receiver——栈能起但告警哪儿也去不了，"可观测"并没有变成"有人响应"。

⑥ 恢复脚本含 --create 导致目标库名冲突——pg_dump --create 会在 SQL 里写 CREATE DATABASE 原始库名，恢复演练到临时库时表没落到临时库。去掉 --create 后演练通过。

⑦ Postgres 序列不同步：全新库首次建院区必崩——迁移 0b8ce330fa1c 用裸 SQL 显式插入 id=1 的默认租户做存量兜底，而 SERIAL 序列不会被显式 id 推进。于是新库上「默认租户占了 id=1、序列还停在 1」，ORM 首次插入租户拿到 id=1 → UniqueViolation；再插一次才成功，看起来像偶发，实则是必现，且只在「新环境建库 / 灾备恢复」时爆炸。加后续迁移用 setval 对齐，并补护栏测试。

"这个 bug 让我明白：alembic check 只比 schema，序列当前值属于数据状态，它查不出来；而且 SQLite 根本不复现——所以必须在全新 Postgres 库上跑一次全量回归，不能只信已有的开发库。"

H. MLOps 与质量工程（4 题）

Q37. prompt 改了之后怎么保证没把模型变笨？

三步闭环：① 版本化——prompt 从代码字符串抽到 src/prompts/v1/*.txt，入 git；② 启动校验——manifest.json 记录 SHA-256，哈希不匹配 fail-closed；③ 回归卡点——scripts/eval_prompt_regression.py --check 检测变更，变更后必须跑 --run-eval 更新 .prompt_baseline.json。

"Prompt 是 LLM 项目最高频的改动，必须当代码资产管。CI 卡不住，靠人肉 review 很容易漏。"
Q38. 怎么做到改 prompt 不影响所有患者？

rollout_configs 表按 feature + scope + percentage 配置灰度；命中优先级 user > tenant > global；用户名做稳定哈希保证同一患者多次请求体验一致；命中时打 Prometheus 指标 medical_agent_rollout_exposures。

Agent 在每次调用前 resolve_version() 决定加载哪个 prompt 版本，未命中回退 v1。

Q39. 幻觉率怎么测？为什么不用 LLM 当裁判？

用 answerable / unanswerable 配对：资料有答案看能否抽对；资料没答案看有没有编造数字。判定规则完全确定性（正则 + must_contain），不依赖另一个 LLM。

不用 LLM-as-judge 的原因：裁判本身也可能幻觉，评分会漂移、不可复现、不可审计。医疗质量 gate 必须是确定性的。

Q40. 备份做了，怎么证明恢复真的能用？

没演练过恢复的备份等于没有备份。本项目有 scripts/restore.py --verify：自动起临时库、恢复 postgres、复制每患者 SQLite、执行健康查询（users/doctors/appointments/tenants 数量），演练后清理临时库。

Runbook 中已记录一次演练结果：备份校验通过，users=59、doctors=3、appointments=2、SQLite 204 个。

"我不只写备份脚本，还写了恢复演练脚本，并且真的跑过一次。事故时按脚本执行就行，而不是现场读文档猜命令。"

I. 可追溯性与成本（2 题）

Q41. 患者投诉「AI 刚才答错了」，你怎么定位？

靠时间戳和用户名翻日志是不可行的——排障的起点必须是唯一可定位的 ID。我的做法是把 trace_id 贯通三层：

① 服务端：入口生成 trace_id，贯穿全部结构化日志；并转成 32 位 W3C 格式，可直接粘进 Jaeger / Tempo 看完整调用链。

② 审计库：chat_logs 记录这轮用的哪个模型、哪个 prompt 版本、所属租户、本轮 token、结果状态（ok / timeout / guard / gate / degraded）与错误原因。

③ 客户端：SSE 首帧 meta 事件把 trace_id 下发给前端，展示成「问题编号」可一键复制。运维 GET /api/trace/{trace_id} 一条命令直达。

「prompt 版本」这一列尤其关键：灰度发布后出问题的往往正是 v2，没有这列你根本判断不了是哪个版本的锅。

"可追溯不是加个日志就算数。患者看到的每条回复下方都有『问题编号』——给我这个号，我能立刻拉出那轮的模型、prompt 版本、token 和完整输入输出。"
Q42. 怎么防止 Agent 失控循环把预算烧穿？

两层：先算得清，再停得住。

归因：真实 usage 优先，取不到按字符估算；双写 Prometheus（低基数维度做趋势告警）与进程内 ledger（含患者维度做即时明细）；每轮 token 同步落审计表，可按需核算。

熔断：调用 LLM 之前预检当日累计用量，≥ 预算就抛 BudgetExceeded，调用方转安全降级话术。支持全局与单患者两级，单患者超限不连坐其他人。触发后打指标告警。

已知边界要主动说：预算计数器是进程内的，多 worker 不共享、重启清零；生产若要严格全局限流应换 Redis 原子计数。

"熔断不只是在故障时用，成本也要有熔断。而且我发现过一个真 bug：意图分类那次 LLM 调用之前完全没算进成本，每轮都少算一笔——这种漏记会让所有成本决策都建立在错误数据上。"
