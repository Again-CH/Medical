## 真实对话演示：填 Deepseek key 跑真人闭环
用户选 B：把 `DEEPSEEK_API_KEY=sk-...` 写入仓库根 `.env`（已被 gitignore，不进提交）。演示脚本 `scripts/demo_deepseek.py` 读该 key → 映射为 `LLM_MODE=openai` + `OPENAI_BASE_URL=https://api.deepseek.com/v1` + `OPENAI_MODEL=deepseek-chat`（Deepseek 走 OpenAI 兼容协议）。
- **沙箱网络**：OpenAI 官方端点不可达（http 000）；**Deepseek 可达**（实测 401=已建连仅 key 无效）。故本环境真实 LLM 只能用 Deepseek。
- **首个真实 bug（致命）**：LangGraph `interrupt()` 在 resume 时会把节点从头重跑；真实 Deepseek 重跑时不再生成敏感工具调用 → `lock_appointment` 没被执行、DB 落库为空。修复：在 `src/agents.py` 引入 `_PENDING` 缓存（按会话线程 ID 稳定 key），命中敏感动作先缓存 tool_calls、`interrupt` 挂起；resume 重跑命中缓存后**直接执行缓存的敏感调用**，不依赖 LLM 重新生成。
- **HITL 统一审批范式（顺带优化）**：非敏感工具即时执行；敏感工具先「累积」不立即执行/挂起；等 LLM 工具轮结束后再「统一一次」interrupt，resume 一次性执行全部敏感动作（医生一次批准 lock+settle，体验更好，也避免分步挂起丢动作）。
- **占位 ToolMessage（API 400 修复）**：延迟执行的敏感 tool_calls 若不补对应 ToolMessage，下一轮把孤儿 tool_call 发给模型报 400。补占位 ToolMessage，内容须明确「尚未执行」避免模型误判已完成而停调后续工具。
- **medicare_settle 偶发漏调**：Deepseek 有时只调 lock 不调 settle。强化 booking 提示「lock+settle 必须同一条消息一起调」+ 占位措辞，复跑稳定触发两工具。
- **`.env` 改 LLM_MODE=openai 一度击穿测试套件**：pytest 经 `config.load_dotenv()` 加载到真实 openai 模式，烧 API 且断言全失败。`tests/conftest.py` 改为导入 src 前强制 `os.environ["LLM_MODE"]="fake"`（load_dotenv 默认不覆盖已存在环境变量）→ 测试 hermetic、确定性、16 passed 回归。
- **最终验证（真实 Deepseek + 真实 Postgres）**：意图分类 booking → 审核门 `action=lock_and_settle tools=['lock_appointment','medicare_settle']` → 医生 `Command(resume={'approved':True})` 后两工具一起执行 → Deepseek 自然回复 → 库内落 `Appointment(id=5, patient=1, doctor=1, 神经内科, 2026-08-28 AM, LOCKED, medicare_settled=True)`。全绿：pytest 16 passed、ruff 全过。
- 注意：`_PENDING` 是模块级全局（单进程有效）；多进程/重启场景应改用 checkpointer 持久化 pending。
